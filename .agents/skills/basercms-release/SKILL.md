# baserCMS リリース手順

baserCMS 本体のパッチリリース（例: 下位系列 5.3.x と上位系列 5.4.x を同じ日に出す）を、リリース担当者と進めるための手順書。
公式の手順は <https://baserproject.github.io/5/collaborator/release> にある。このスキルはそれを現在のブランチ構成に読み替え、実際のリリースで分かった順序と落とし穴を足したもの。食い違ったら、まず現在のリポジトリの状態（ブランチ・前回のタグとコミット）を正とする。

## 0. 前提と原則

- **ブランチ構成**: 系列ごとの開発ブランチ（`5.3.x`、`5.4.x` …）があり、`master` は最上位系列の最新リリースと同じ位置にある。
- **順序**: 下位系列 → 上位系列の順に出す。下位系列の修正を上位系列へマージしてから上位を出すため。
- **対外的・不可逆な操作は、必ず実行前に担当者の承認を得る**。該当するのは、開発ブランチ・`master` への push、タグの push、アドバイザリ fork の PR のマージ、GitHub Release・セキュリティアドバイザリ・公式サイトのページの公開、告知の送信、ブランチの削除。
- **認証情報は担当者が入力する**。サーバーへのログイン、管理画面やチャットへのサインインは担当者に頼み、パスワードをスキルやリポジトリ、コミットに書かない。
- **リリースコマンド（`monorepo-builder release`）は担当者に実行してもらってよい**。エージェントの実行環境が破壊的操作として止めた場合は、回避せずコマンドを提示する。
- **前例に合わせる**。コミットメッセージ、リリース記事、告知文は、前回の同じ系列のものを取得して雛形にする。書式を新しく作らない。
- **公開リポジトリに出るもの**（コミット、PR、リリース記事）に、未公開の脆弱性の内容、再現手順、ローカルのパス、認証情報を書かない。

### 環境ごとの値

公式サイトのサーバー接続先、管理画面の URL、脆弱性の管理表の場所、告知先のチャンネルなど、担当者や組織ごとに違う値はこのスキルに書いていない。
`~/.config/basercms-release/local.md` があれば最初に読み、そこに書かれた値と手順を使う。無ければ、必要になった時点で担当者に確認する（答えをこのファイルに残しておくと次回から聞かずに済む。認証情報は書かない）。

## 1. 全体の流れ

| # | 工程 | 補足 |
|---|---|---|
| 1 | 事前確認 | 脆弱性修正の有無、新規プラグインの登録、対象バージョン |
| 2 | 脆弱性修正の取り込み（ある場合） | アドバイザリ fork の PR を下位系列へ |
| 3 | 下位系列のリリース | VERSION.txt → composer.json → タグ |
| 4 | 下位系列を上位系列へマージ | 競合の解き方は 4 章 |
| 5 | 上位系列の VERSION.txt と push | |
| 6 | アップデートテスト（上位系列のみ） | 開発版を使う |
| 7 | 上位系列のリリース | `master` へマージ → release コマンド |
| 8 | 開発版へ番号を戻す | 両系列 |
| 9 | 配布パッケージ（zip）の作成 | |
| 10 | 公開 | 出す順番は 9 章 |
| 11 | 告知 | |
| 12 | 後片付け | |

工程ごとに、やったこと・確認結果・未完了を短く報告し、対外操作の前で止まって承認を得る。

## 2. 事前確認

1. **対象バージョンを決める**: 各系列の `plugins/baser-core/VERSION.txt` の 1 行目（`X.Y.Z-dev`）と `git tag` の最新を見て、今回出す版を担当者と確認する。
2. **脆弱性修正を含むかを確かめる**: リリース日が今回の日付になっている脆弱性を、担当者の管理表やセキュリティアドバイザリの一覧（`gh api /repos/baserproject/basercms/security-advisories?state=draft`）で洗い出す。含めるかどうかは担当者が決める。対象・修正版の記入漏れもこの時点で点検する。
3. **新規プラグインの登録を確かめる**: `plugins/` のディレクトリと `.github/workflows/split_monorepo.yml` の `local_path` を突き合わせる。前回のリリース以降に増えたプラグインがあれば、分割先リポジトリと Packagist への登録が先に必要（`basercms-core-plugin-convert` を参照）。
4. **必要なスキルを先に読む**: `basercms-release-note` などのスキルがリポジトリの上位系列のブランチにしか無い場合、下位系列へ切り替えると作業ツリーから消える。切り替える前に読んでおく。
5. **作業ツリーをきれいにする**: `git status --short` が空であること。release コマンドは未追跡ファイルもコミットに巻き込むので、残したい未追跡ファイルは `.git/info/exclude` に一時的に足して外す（終わったら戻す）。
6. ブランチを切り替えたら `composer install` をやり直す（vendor が別系列の状態で残ると、プラグインを見つけられずテストが落ちる）。

### 脆弱性修正の取り込み

- アドバイザリ fork の PR の mergeable 表示は、**fork 内の古い base との比較**なので信用しない。本家の最新の base へローカルで統合し、競合とテスト結果を確かめる。
- 競合したら、修正ブランチへ base をマージする向きで解消コミットを作り、検証済みのツリーと差分が無いことを確かめてから fork へ push する。
- 本家へのマージは、アドバイザリ画面の「Merge pull request」で行う（ブランチ保護を越える操作なので、担当者が押すか、明示の承認を得る）。base には「Merge commit from fork」という 1 コミットで入る。
- 取り込みの確認は、push したコミットと `origin/<base>` の `git diff --stat` が空であることで行う。
- 検証・fork・PR の詳しい手順は `basercms-security-advisory` を参照する。

## 3. 下位系列のリリース

下位系列のブランチで行う。**前回の同じ系列のリリースのコミット構成を `git log` で確かめ、同じ形にする**。

1. `git pull` する。
2. `vendor/bin/monorepo-builder merge` を実行する。ルートの `composer.json` がキーの並び替えだけ（JSON として同じ内容）なら変更を戻し、`composer.lock` も触らない。中身が変わったときだけ lock を更新してコミットする。
3. **VERSION.txt を更新する**（`basercms-release-note`）。1 行目を `X.Y.Z` にし、リリースブロックを追加する。セキュリティ修正の行は攻撃手法を書かず、アドバイザリの番号だけ添える。コミットメッセージは前例どおり（例「baserCMS X.Y.Z をリリース」）。
4. **`plugins/baser-core/composer.json` のコアプラグインの版を `X.Y.x-dev` から `X.Y.Z` に変える**。対象の数は系列ごとに違うので、公式手順の個数ではなく `grep` の件数で確かめる。別コミットにする。
5. 開発ブランチへ push する（承認）。
6. **タグを付ける**。下位系列は前回と同じ方法にする。手動タグ（`git tag X.Y.Z` → `git push origin X.Y.Z`）で出している系列なら、それに合わせる。release コマンドを使う場合は 6 章の注意（タグの検査）を読む。
7. タグの push で動く GitHub Actions（Packages Split など）の成功を確かめ、`composer show --all baserproject/baser-core` で新しい版が見えることを確かめる。**Packagist の反映を待たずに次の工程へ進んでよい**。

下位系列ではアップデートテストをしない（最上位系列でだけ行う）。

## 4. 下位系列を上位系列へマージ

上位系列のブランチで `git merge origin/<下位系列>` を行う。毎回ほぼ同じ場所が競合する。

| ファイル | 解き方 |
|---|---|
| `plugins/baser-core/VERSION.txt` | 上位側を採用する。下位系列のリリースブロックは上位の VERSION.txt に足さず、同じ内容の行を上位の今回のブロックに含める（前回の上位系列のブロックの書き方に合わせる） |
| `plugins/baser-core/composer.json`、ルートの `composer.json`・`composer.lock` | 上位側を採用する |
| 設定ファイル（`config/setting.php` など） | 両系列の追加を両方残す |
| 同じ処理を両系列で別々に直したコード | 下位系列で検証済みの順序・実装を採用し、上位側に残った重複する判定を外す。関連テストは両方残す |

解消後、競合したファイルに関わるテストを流し（`basercms-unittest`）、失敗が無いことを確かめてからコミットする。

続けて上位系列で 3 章の 2〜3（merge コマンド、VERSION.txt）を行い、開発ブランチへ push する（承認）。上位系列の VERSION.txt は、前回の上位リリース以降のコミットに加えて、下位系列から入った修正も対象にする。マイグレーションやアップデーターの追加があるかもここで確かめる。

## 5. アップデートテスト（最上位系列のみ）

上位系列の開発ブランチを push すると、Packages Split が終わったあと `X.Y.x-dev` が Packagist に反映される。それを使って、ひとつ前の版から管理画面でアップデートできるかを確かめる。公式の手順は <https://baserproject.github.io/5/collaborator/update_test>。

1. **テスト環境を確かめる**: アップデートテスト用の環境（composer でインストールした baserCMS。`baser-core` を `X.Y.x-dev`、`minimum-stability` を `dev` にしてあり、`replace` が無いもの）。場所は環境ごとの値を見る。無ければ担当者に確認する。
2. **事前の記録**: 環境を git で管理している場合は、先に `git status` を見る。未コミットの変更があれば、その時点の版の名前でブランチを作ってコミットし、アップデート前の状態を残す。
3. **実行**: 管理画面のアップデート画面（`/baser/admin/baser-core/plugins/update`）で「最新の開発版をダウンロードする」にチェックしてダウンロードし、利用可能なバージョンが今回の版になったら「アップデート実行」を押す。デバッグモードが必要。
4. **判定**: 完了メッセージ、プログラムとデータベースのバージョンが両方とも今回の版、`logs/update.log` に全プラグインの完了が出ていること、`vendor/baserproject/baser-core/VERSION.txt` の 1 行目。
5. **事後の記録**: 今回の版の名前でブランチを作ってコミットする。

ブラウザを自動操作する場合の注意:
- ローカル環境が自己署名証明書だと、開けないブラウザがある。開けるブラウザを使う。
- 「アップデート実行」はブラウザ標準の確認ダイアログを出し、自動操作が止まることがある。ローカルのテスト環境に限り、押す前に `window.confirm` を常に true を返す関数に差し替えると進められる。
- ログインに使う値は、テスト環境の `composer.json` のインストールスクリプトなど、環境側の定義を参照する。値をスキルや報告に書き写さない。

Packagist に開発版が反映される前にダウンロードすると古い内容になる。Packages Split の成功を確かめてから始める。

## 6. 上位系列のリリース

1. `master` を pull し、上位系列の開発ブランチをマージする（fast-forward になる）。
2. `plugins/baser-core/composer.json` のコアプラグインの版を `X.Y.Z` に変えてコミットする（3 章の 4 と同じ。上位系列はプラグインが増えていることがある）。
3. `git status --short` が空であることを確かめる。
4. `php vendor/bin/monorepo-builder release X.Y.Z --dry-run` で、行われる工程（ルート `composer.json` の `replace` 更新 → タグ → タグの push）を確かめる。
5. `php vendor/bin/monorepo-builder release X.Y.Z` を実行する（承認。担当者が実行してもよい）。途中で「master ブランチでリリースしてよいか」と聞かれるので yes と答える。「prepare release」コミットが作られ、`master` とタグが push される。
6. `master` を上位系列の開発ブランチへマージして push する。
7. タグの Packages Split の成功と、`composer show --all` で今回の版が見えることを確かめる。

release コマンドの注意（詳しくは `basercms-security-advisory` の落とし穴レシピ）:
- 「ローカルにあるタグのうち最新の日付のもの」より大きい版しか通さない。上位系列を先に出したあとで下位系列を release コマンドで出すときは、作業用クローンで上位のタグをローカルだけ消してから実行し、終わったら `git fetch origin --tags` で戻す。
- 未追跡ファイルを巻き込む。実行前に `git status --short` を必ず見る。
- 誤ってタグを出したときは、本体だけでなく分割先の全リポジトリからタグを消す必要がある。

## 7. 開発版へ番号を戻す

タグを出したら、両方の系列ブランチで次の版の開発版に戻す。

- `plugins/baser-core/VERSION.txt` の 1 行目を `X.Y.(Z+1)-dev` にする。
- `plugins/baser-core/composer.json` のコアプラグインの版を `X.Y.x-dev` に戻す。
- ルート `composer.json` の `replace` は触らない。
- 上位系列は `master` をマージした状態から行う。
- コミットメッセージは各系列の前例に合わせ、push する（承認）。

## 8. 配布パッケージの作成

コンテナの中で作る。

```
bin/cake create release X.Y.Z                    # 最上位系列
bin/cake create release X.Y.Z --branch 5.3.x     # 下位系列（ブランチは --branch で指定）
```

- 出力は `tmp/basercms-X.Y.Z.zip`。
- `unzip -p <zip> composer.json` で `baser-core` の版が今回の版になっているかを確かめる。
- 失敗するときは Packagist への反映待ちのことが多い。数分おいてやり直す。
- 前の版とサイズが大きく違うときは、中身の一覧を比べて理由（配布物から外したファイルなど）を説明できるようにしておく。

## 9. 公開の順番

リンク切れが起きないよう、**リンクされる側を先に公開する**。

1. **公式サイトの脆弱性情報ページ**（脆弱性修正を含む場合）。リリース記事とアドバイザリからリンクするので最初に作る。影響範囲は、各タグの該当ファイルに修正が入っているかを `git show <タグ>:<ファイル>` で確かめて書く。1 件だけのときに題名や導入文を「複数の脆弱性」としない。攻撃手順は書かない。
2. **zip を公式サイトへアップロードする**。置き場所と方法は環境ごとの値を見る。アップロード後、公開 URL に HEAD リクエストを送り、サイズが手元のファイルと一致することを確かめる。公式サイトが表示する「最新バージョン」がキャッシュで古いままになることがあるので、表示が新しい版に変わったことまで確かめる（変わらないときの対処は環境ごとの値を見る）。
3. **GitHub Release を公開する**（次節）。
4. **セキュリティアドバイザリを公開する**（脆弱性修正を含む場合。次々節）。
5. **公式サイトのダウンロードページを更新する**。ボタンの版、最終リリース日、過去バージョンの表（版・サイズ・日付・リリースノートへのリンク）。
6. **公式サイトのリリース記事を公開する**。前回のリリース記事を複製して、題名・概要・本文の版番号・変更内容の説明・脆弱性情報ページへのリンク・投稿日を差し替える。非公開のまま保存して内容を担当者に見せ、承認後に公開する。

公式サイトのページは、公開後にログインしていない状態で取得し、ページが開けること・版番号・リンク先を確かめる。

### GitHub Release

- **前回の同じ系列の本文を雛形にする**: `gh release view <前の版> --json body` で取得する。冒頭（発表文、脆弱性の一覧、脆弱性情報ページとダウンロードのリンク）と変更内容（VERSION.txt の今回のブロックを 新機能／変更点／バグフィックス に分ける）を差し替え、「インストールする」以降の定型部分は版番号だけ置き換える。
- **開発貢献者**: `git log <前のタグ>..<今回のタグ> --format=%an` の重複を除いたもの（依存更新のボットは除く）。
- まず下書きで登録する。

```
gh release create X.Y.Z tmp/basercms-X.Y.Z.zip --draft --verify-tag --title "baserCMS X.Y.Z リリース" --notes-file <本文>
```

- 下位系列には `--latest=false` を付ける。
- 担当者の確認後に公開する。下位系列 → 上位系列の順で、上位に `--latest` を付ける。

```
gh release edit <下位の版> --draft=false --latest=false
gh release edit <上位の版> --draft=false --latest
```

- `gh api /repos/baserproject/basercms/releases/latest` が上位の版を返すことと、添付 zip の URL を確かめる。下書きの URL は編集のたびに変わるので、一覧は API で取り直す。

### セキュリティアドバイザリの公開

1. **影響範囲と修正版を最終確認する**。影響範囲の上限は「修正を含まない最後の公開版」まで。修正を前のリリースから見送っていた場合、報告時の範囲のままだと直近の版が対象外に読めてしまう。
2. **報告者への連絡は公開の前にコメントする**。公開後のアドバイザリにはコメントを追加できない。修正版と公開日を伝えるコメントは、公開の操作より先に投稿する。
3. **本文を読み直す**。報告者のメールアドレスなど個人の連絡先が含まれていたら、公開前に担当者に扱いを確認する。
4. 公開する（承認）。

```
gh api --method PATCH /repos/baserproject/basercms/security-advisories/<GHSA-ID> --input <影響範囲と修正版の JSON>
gh api --method PATCH /repos/baserproject/basercms/security-advisories/<GHSA-ID> -f state=published
```

5. 公開後、ページを読み込み直して Published・影響範囲・修正版の表示を確かめる。CVE が未採番でも公開してよい。採番されたら、脆弱性情報ページなどへ追記する。

## 10. 告知

- 告知先（フォーラム、コミュニティのチャット、広報担当への依頼など）は環境ごとの値を見る。無ければ担当者に確認する。
- **文面は、それぞれの場所の前回の投稿を読んで同じ形にする**。一般的な構成は、リリースの特徴を一言、セキュリティ修正を含む旨、脆弱性情報ページへのリンク、アップデートのお願い、リリース記事へのリンク。
- 下書きを担当者に見せて承認を得る。投稿先に入力したあと、**送信の直前にもう一度画面を見せて確認を取る**。全員宛ての通知（チャンネル全体へのメンションなど）は、通知される人数の確認が出る。
- 投稿後、表示された投稿とリンクを確かめる。

## 11. 後片付け

- 作業を始めたときのブランチへ戻し、`composer install` をやり直す。
- `.git/info/exclude` に足した行を消す。
- 検証用に作ったローカルブランチは、内容が本家に取り込まれたことを差分で確かめたうえで、一覧を示して承認を得てから削除する。
- 脆弱性の管理表や課題管理に、対象・修正版・公開した URL・CVE の状況を記録する（場所は環境ごとの値）。
- 一時的に置いた認証用のファイルがあれば、担当者に削除を頼む。
- 残っていること（CVE の採番待ちなど）を報告に明記する。

## 12. 落とし穴

- **mergeable 表示を信じない**: アドバイザリ fork の PR は、本家の最新とは競合していることがある（2 章）。
- **並び替えだけの差分をコミットしない**: `monorepo-builder merge` の結果は JSON の中身で比べる（3 章）。
- **コアプラグインの数は系列で違う**: `composer.json` の書き換え箇所を個数で決め打ちしない（3 章）。
- **下位系列のブロックを上位の VERSION.txt に二重に書かない**（4 章）。
- **アップデート実行の確認ダイアログで自動操作が止まる**（5 章）。
- **release コマンドは未追跡ファイルを巻き込み、タグの新旧を検査する**（6 章）。
- **公開の順番を崩さない**: zip のアップロードより先に GitHub Release を公開したり、脆弱性情報ページより先にリリース記事を出したりすると、リンク切れになる（9 章）。
- **アドバイザリ公開後は報告者にコメントできない**（9 章）。
- **公式サイトの最新バージョン表示はキャッシュで遅れることがある**（9 章）。
- **Packagist の反映は数分遅れる**: 配布パッケージの作成やアップデートテストが古い版を掴んだら、時間をおいてやり直す。

## 13. 関連スキル

- `basercms-release-note`: VERSION.txt のリリースブロックの作成。
- `basercms-security-advisory`: 脆弱性の検証、アドバイザリ fork・PR、リリース後の取り込み確認、リリース作業の落とし穴レシピ。
- `basercms-unittest`: ユニットテストの実行。
- `basercms-core-plugin-convert`: 新しいコアプラグインの分割先リポジトリ・Packagist への登録。
